# 06. Мини-проект и индивидуальная защита

**Цель:** Самостоятельно применить полный цикл к новой функции сопоставимой сложности и доказать результат конкретными проверками.

**Рабочая ветка:** `final/<short-feature-name>`

## Выберите одно требование

### A. Счётчик по статусам

Добавьте `countTicketsByStatus(tickets)`.

Успешный контракт:

```js
countTicketsByStatus(tickets) // { open: 4, closed: 2, total: 6 }
```

Функция не мутирует вход. UI одновременно показывает `Открытые: 4`, `Закрытые: 2`, `Всего: 6`.

### B. Фильтр по приоритету

Добавьте `filterTicketsByPriority(tickets, priority)`.

Успешный контракт:

- `all → [1,2,3,4,5,6]`;
- `high → [1,3]`;
- `normal → [2,4,6]`;
- `low → [5]`;
- неизвестное значение → `RangeError`;
- вход не мутируется.

### C. Сохранение выбранного статуса

После выбора фильтра `open` или `closed` и перезагрузки страницы выбранное значение восстанавливается из `localStorage`.

Успешный контракт:

- новое посещение без сохранённого значения → `all`;
- сохранено `open` → после reload выбран `open` и показаны 4 заявки;
- сохранено `closed` → после reload выбран `closed` и показаны 2 заявки;
- неизвестное сохранённое значение → безопасный fallback на `all`, ошибок в консоли нет.

### D. Сброс фильтров

Добавьте кнопку `Сбросить` для уже существующих status/search/sort.

Успешный контракт после нажатия:

- status = `all`;
- строка поиска пустая;
- сортировка возвращается к исходному порядку ID `[1,2,3,4,5,6]`;
- показаны 6 заявок;
- повторное нажатие не меняет результат и не вызывает ошибок.

Другая функция допускается только после согласования **до начала кодирования**, если преподаватель письменно фиксирует такой же конкретный контракт с входами и ожидаемыми выходами.

## Полный цикл

1. Создайте задачу GitVerse и вставьте в неё выбранный контракт без размытых формулировок.
2. До запуска агента запишите минимум четыре проверки: обычная, граничная, ошибочная и проверка отсутствия побочного эффекта.
3. Создайте ветку и получите план агента.
4. Найдите минимум один риск или пробел плана и исправьте его до изменения кода.
5. Выполните ограниченную правку и просмотрите diff.
6. Добавьте автоматические тесты для выбранного контракта.
7. Запустите полный `npm test` и четыре ручных сценария.
8. Создайте Merge Request, дождитесь зелёного CI и выполните review.
9. Заполните `HANDOFF.md`: что изменено, точные шаги проверки, что не проверено.
10. Подготовьте индивидуальную защиту на новом входе преподавателя.

## Успешный результат

- выбран **один** из контрактов A–D и все его конкретные значения выполняются;
- к существующим 19 тестам добавлено минимум **4 новых теста**, поэтому `npm test` показывает не менее **23 успешных тестов**;
- GitVerse CI зелёный на финальном commit;
- четыре ручных сценария в `REPORT.md` содержат поля `вход → ожидание → фактический результат → PASS/FAIL`, и все обязательные сценарии имеют PASS;
- MR не содержит несвязанных изменений и новых dependencies без отдельного согласования;
- `HANDOFF.md` позволяет другому студенту воспроизвести проверку без устных пояснений;
- на защите студент сначала прогнозирует результат нового входа, затем запускает проверку и объясняет расхождение, если оно есть.

## Не засчитывается, если

- результат описан фразой «вроде работает» без точных входов и выходов;
- тесты проверяют не тот контракт, который записан в задаче;
- CI зелёный на старом commit, а финальный код не проверен;
- студент не может объяснить минимум одну внесённую функцию или решение;
- `HANDOFF.md` скрывает непроверенные части или содержит только пересказ ответа агента.

## Что сдавать

- ссылка на задачу GitVerse с конкретным контрактом;
- Merge Request и зелёный CI;
- `REPORT.md` с минимум четырьмя сценариями и выводом `npm test`;
- `HANDOFF.md`;
- индивидуальная защита.

## Защита

Преподаватель меняет один вход в рамках выбранного контракта. Студент **до запуска** говорит ожидаемый результат, затем проверяет его. Количество запросов к AI, бренд модели и красивый интерфейс сами по себе баллов не дают.

## Что принимает преподаватель

- все конкретные значения выбранного контракта совпадают
- добавлены минимум четыре содержательных теста и весь suite зелёный
- MR/CI относятся к финальному commit
- студент воспроизводит новый сценарий и объясняет результат без чтения ответа агента
