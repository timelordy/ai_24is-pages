## Задание

Продолжим Campus ServiceDesk из первой работы. Сейчас на странице 12 заявок, нужную приходится искать глазами.

Добавим поле: при вводе `305` останется заявка №101 о проекторе в этой аудитории, а счётчик покажет 1. Затем сохраним проверенную версию и отправим её преподавателю.

## 1. Создай свою копию на GitVerse

- **Git** хранит историю изменений на компьютере.
- **GitVerse** хранит репозиторий (repository), файлы вместе с историей, в интернете.
- **Fork, или форк**, создаёт копию репозитория в твоём аккаунте GitVerse. Форк появится на GitVerse; папка на компьютере пока останется прежней.
- **Clone, клонирование**, скачивает файлы и историю на компьютер.

Если папка первой работы сохранилась, обычно повторно скачивать её не нужно.

1. Войди на GitVerse. Если аккаунта ещё нет, нажми **«Вход»**, выбери доступный способ регистрации и следуй подсказкам. При затруднении покажи преподавателю экран, на котором остановился.
2. Открой [Campus-ServiceDesk преподавателя](https://gitverse.ru/ultra_turbo_killer/Campus-ServiceDesk). Над файлами должен быть владелец `ultra_turbo_killer`. Репозиторий `ai_24is-pages` на GitHub содержит методичку; для работы нужен именно Campus-ServiceDesk.
3. Нажми **«Форк»**, выбери свой аккаунт и нажми **«Форкнуть репозиторий»**. Если свой форк уже есть, открой его. Проверь: перед Campus-ServiceDesk в заголовке и адресе страницы указан твой логин.
4. В своём форке открой **«Код → Клонирование → HTTPS»**. Скопируй адрес, в котором после `gitverse.ru` указан твой логин. Он нужен на следующем шаге.

[Официальная инструкция GitVerse по Fork](https://gitverse.ru/docs/collaborative/repositories/guides/repository-workflow/fork-repo/).

## 2. Подключи прежнюю папку и рабочую ветку

- **Ветка**, именованная линия истории проекта, позволяет продолжить сохранённую версию отдельно.
- **Коммит** сохраняет в истории Git снимок подготовленного состояния проекта с подписью.
- **Сохранение файла** через `Ctrl+S` лишь записывает текст на диск.

От текущей версии первой работы создадим `feature/frontend-query`. До правки это тот же сайт с 12 заявками. Позже коммит поиска продолжит новую ветку, а прежняя ветка останется на исходной записи.

Косая черта в имени не создаёт папку.

`origin` означает короткое имя сохранённого в Git адреса удалённого репозитория. После Clone это обычно адрес скачанного проекта:

- **Получение истории:** адрес `fetch`.
- **Отправка:** адрес `push`.

Смена `origin` не меняет файлы и ничего не отправляет.

1. В VS Code открой прежнюю папку `Campus-ServiceDesk` через **«Файл → Открыть папку»**. Найди свою заметку, сохрани её и сделай копию вне проекта. Она может называться не `REPORT.md`.

Слева должны быть видны `package.json`, `server.mjs` и `src`.

2. Выбери **«Терминал → Создать терминал»**. Терминал принимает точные команды программ и показывает их ответы. Не вводи их в поле сообщения OpenCode; путь возле курсора должен заканчиваться именем проекта.

Команды ниже показывают:

- `git status --short`: краткий (`--short`) список изменений вне коммита.
- `git remote -v`: подробные (`-v`) адреса удалённых репозиториев.
- `git branch --show-current`: имя текущей ветки (`--show-current`).

Выполни строки по одной, после каждой нажми Enter:

```text
git status --short
git remote -v
git branch --show-current
```

Если первая команда перечислила файлы, открой их и сохрани нужную работу в текущей ветке до переключения. Можно попросить агента показать разницу, выбрать только твою заметку и подготовку, затем после твоего подтверждения сделать коммит, как в работе 01. Непонятные изменения покажи преподавателю; не удаляй их ради пустого вывода.

3. До смены `origin` проверь происхождение истории. Если первая работа скачана через Clone, история преподавателя уже есть.

Если использовал ZIP или не помнишь способ, запусти `opencode.cmd` в терминале проекта, клавишей Tab выбери **Plan** и попроси прочитать историю без изменений: есть ли общие прежние коммиты с исходным проектом и форком?

При отдельной истории обратись к преподавателю. Вместе клонируйте свой форк в другую папку и перенесите только заметку. Старую папку сохрани.

Не переноси готовый код из другой истории, не применяй `reset`, `force` или `--allow-unrelated-histories`, объединение несвязанных историй.

4. Сравни адреса `git remote -v` с адресом своего форка из шага 1. Если обе строки уже верны, ничего не меняй. Иначе запусти `opencode.cmd` в терминале проекта и передай агенту настоящий адрес.

Попроси предложить подходящую команду:

- `git remote set-url origin` с этим адресом заменяет сохранённый адрес `origin`.
- Если `origin` отсутствует, `git remote add origin` добавляет его.

**Сверь владельца** в предложенной команде и разреши её в **Build**. Затем открой другой обычный терминал и повтори `git remote -v`. В обеих строках, `fetch` и `push`, должен быть твой аккаунт.

Если `push`-адрес остался чужим, остановись и покажи преподавателю.
5. Повтори `git status --short`. `git switch` переключает ветку, а `-c` просит сначала создать новую от текущего коммита. Имя `feature/frontend-query` вводи целиком. При пустом выводе и выбранной сохранённой версии первой работы выполни:

```text

```

Если ветка уже есть, при чистом состоянии выполни `git switch feature/frontend-query` без `-c`. При ошибке не пересоздавай её, покажи текст преподавателю. В ответе Git должна быть выбрана `feature/frontend-query`.

6. Скачай TASK работы 02 или передай его текст агенту. Если заменяешь прежний TASK.md, проверь, что в нём не осталось своих записей. REPORT скачивай по желанию; прежнюю заметку им не заменяй. Сохрани рабочий `opencode.json` без ключей.

Если прежней папки нет, в VS Code нажми `Ctrl+Shift+P`, выбери «Git: Clone / Git: Клонировать», вставь HTTPS-адрес своего форка и выбери новое место. Открой скачанную папку, проверь адреса командами выше и перенеси прежнюю заметку вручную, если она доступна.

## 3. Согласуй план и поручи агенту поиск

OpenCode, локальная программа на компьютере, принимает поручения в собственном поле сообщения. Обычные команды Git вводи в другом терминале VS Code. Модель ИИ составляет ответы и выбирает действия; инструменты OpenCode читают файлы, меняют их и запускают команды.

Tab переключает режимы:

- **Plan** («планирование») нужен для чтения и обсуждения.
- **Build** («выполнение») позволяет согласованные изменения.

Это режимы доступа к инструментам, а не разные модели.

Используй подключение первой работы. Запрос уходит через интернет провайдеру, сервису компании, который выполняет выбранную модель на своих серверах.

Прочитанные агентом файлы могут попасть в запрос как контекст, сведения для ответа; вся папка автоматически не отправляется. Используй учебные несекретные данные. API-ключ, секрет программного доступа к сервису ИИ, не вставляй в сообщения или файлы сайта.

Если агент недоступен, обратись к преподавателю; **оплачивать подключение ради занятия не требуется**.

### Сначала план

Запусти `opencode.cmd` в терминале проекта, выбери **Plan** клавишей Tab и отправь в поле OpenCode:

```text
Хочу находить заявки по слову или аудитории, например по запросу 305. Добавь поле поиска и число найденных заявок. Если ничего не найдено, страница должна об этом сообщать.

Сначала прочитай TASK занятия 02 и связанные с поиском файлы. Пока ничего не меняй.

Предложи короткий план: какие файлы изменить, что может перестать работать и как это проверить. Учти правила поиска из TASK и добавление тестов. Пока занимаемся только поиском.
```

Добавь свой пример: кому и какую заявку нужно найти. Прочитай план, согласуй пути файлов и границы правки. Если пункт непонятен, попроси объяснить его до изменений. Дополнительный вопрос ради самого вопроса не нужен.

### Правила поиска

- Ищем по `title` (заголовку), `description` (описанию) и `location` (месту заявки). Подходит и часть текста: `проект` найдёт заявку о проекторе.
- Большие и маленькие буквы считаются одинаковыми. `trim`, удаление пробелов по краям текста, позволяет запросам `ПРОЕКТОР` и `  проектор  ` находить одну заявку.
- Пустой запрос показывает все 12 исходных заявок. На странице видны число найденных заявок и сообщение, если ничего не найдено.
- Исходные массив и объекты не изменяются: поиск возвращает подходящий список, не удаляя заявки из исходных данных.
- Можно использовать `applyTicketQuery(tickets,{search})`: функцию, которая принимает список заявок и запрос, а возвращает новый список. Это допустимый вариант, не обязательное имя.
- Не добавляй фильтры, сортировку, HTTP API (дополнительные способы обращения к данным приложения из других программ), БД (базу данных), вход пользователей или библиотеки. API приложения и личный API-ключ модели ИИ относятся к разным задачам.

### Затем изменения

Тест автоматически выполняет заданную проверку и сравнивает результат с ожидаемым. npm, программа из установки Node.js, умеет запускать готовые команды проекта. `npm test` запускает команду тестов из `package.json`, файла настроек проекта.

Тесты поиска должны проверять:

- Все три поля и совпадения.
- Регистр и пробелы по краям.
- Пустой запрос и отсутствие совпадений.
- Неизменность исходных массива и объектов.

Нельзя менять ожидаемые результаты ради ошибочного кода.

Проверь каждое поле отдельно: в тестовой заявке искомое слово должно быть только в заголовке, только в описании или только в месте. `305` есть и в описании, и в месте заявки №101, поэтому один этот пример не доказывает проверку обоих полей. Добавь проверку части текста, например `проект`. Тестовые заявки создавай в тестах, исходные 12 заявок не меняй.

Переключись в **Build**, перечисли согласованные файлы и отправь:

```text
Сделай поиск по согласованному плану только в перечисленных нами файлах. Сохрани исходные заявки и прежние возможности сайта.

Добавь тесты по TASK занятия 02 и запусти npm test. Покажи результат, какие файлы изменены и что осталось непроверенным.
```

## 5. Сохрани и отправь рабочую ветку

Теперь при `305` остаётся заявка №101. Зафиксируем эту версию:

1. **Сохранение файла:** `Ctrl+S` записывает файлы на диск.
2. **Staging:** подготовка через **+** выбирает изменения для следующего снимка.
3. **Commit:** сохраняет снимок в локальной истории.
4. **Push:** отправляет ветку с коммитами в форк.

**До push результат на GitVerse не появится.**

У коммита есть SHA, идентификатор из букв и цифр.

- **До отправки:** коммит поиска есть только на компьютере.
- **После push:** тот же коммит можно открыть в `feature/frontend-query` своего форка и сверить SHA, чтобы подтвердить совпадение версий.

Правки вне коммита не отправляются, `main` остаётся прежней. Push не запускает сайт в интернете: поиск показываем в локальном браузере.

Запрос на слияние и автоматическая проверка на GitVerse для этой работы не требуются.

1. Сохрани файлы через `Ctrl+S`. В **«Управлении версиями»** нажми **+** только возле проверенных файлов поиска и подготовки этой работы. Это staging, ещё не коммит.

Не выбирай ключи, `.env` (файл локальных настроек и секретов), базу и посторонние файлы.

- Если выбрал лишнее, кнопка **−** убирает файл из подготовки, но не удаляет с диска.
- Если редактировал файл после **+**, проверь его и повтори **+** для нового текста.

2. Перед коммитом проверим ветку, адреса и подготовленные изменения. `git diff --cached` показывает только подготовку: `--cached` означает выбранный набор будущего коммита. В обычном терминале выполни:

```text
git branch --show-current
git remote -v
git diff --cached
```

Первая команда должна показать `feature/frontend-query`, вторая адрес твоего форка для fetch и push. Прочитай изменения из третьей команды. Если открыт длинный вывод с двоеточием внизу, прокручивай стрелками и нажми английскую `q`, чтобы вернуться к командам.

3. `git commit` сохраняет снимок подготовленного состояния проекта. `-m` означает, что дальше задано сообщение коммита. Кавычки объединяют слова в одну подпись.

`feat: add ticket search` значит «добавлен поиск заявок». `feat:` принято использовать для новой возможности; это необязательное соглашение, не специальная команда. Здесь можно скопировать подпись целиком:

```text
git commit -m "feat: add ticket search"
```

Git должен показать новый коммит в `feature/frontend-query` с этой подписью. Если просит имя и почту автора, попроси агента настроить их только для этого проекта, затем повтори команду. Если Git сообщает, что сохранять нечего, не создавай пустой коммит: проверь подготовку и последнюю запись истории.

4. `git push` отправляет коммиты. `origin` выбирает адрес твоего форка, `feature/frontend-query` выбирает ветку. `-u` запоминает связь локальной ветки с удалённой для следующих отправок:

```text
git push -u origin feature/frontend-query
```

В успешном ответе есть адрес твоего форка и `feature/frontend-query -> feature/frontend-query`, без ошибки отправки.

GitVerse может запросить вход: следуй его окну авторизации, **не вводи туда ключ Inception**.

Если push отклонён, покажи текст преподавателю. Не используй `force`, принудительную перезапись истории, и не сбрасывай историю.

## 6. Покажи коммит, поиск и своё объяснение

- **SHA**, идентификатор коммита из букв и цифр, позволяет проверить, что на компьютере и GitVerse одна версия.
- **Выбранный коммит** обозначается `HEAD`.

Первая команда печатает полный SHA; вторая показывает одну (`-1`) последнюю запись кратко (`--oneline`), с сокращённым SHA и подписью. Выполни строки по одной в обычном терминале:

```text
git rev-parse HEAD
git log -1 --oneline
```

Открой свой форк на GitVerse, выбери `feature/frontend-query` над файлами и открой последний коммит. Сравни полный SHA с `git rev-parse HEAD`. Скопируй ссылку на коммит для преподавателя.

Покажи поиск по сценариям шага 4 и объясни без агента одно решение: например, зачем убирать пробелы или искать в трёх полях. Покажи свой запрос, согласованный план, просмотренные изменения и результат тестов. Скажи, что проверено и что осталось непроверенным.
