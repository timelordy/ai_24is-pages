# 03. Готовая форма и курсор после создания

**Цель:** Подключить готовую форму, сохранив свой поиск. После успешного создания вернуть курсор в поле «Краткий заголовок» (в коде `title`), чтобы следующую заявку можно было начинать с клавиатуры. При ошибке ввод и поиск должны сохраниться.

**Рабочая ветка:** `feature/ticket-api`

## Готовая основа и твой вклад

Работаем в прежней папке `Campus-ServiceDesk` с принятым поиском 02 и своим **форком**, личной копией репозитория на GitVerse.

**Foundation** означает готовую основу. Это полный работающий накопительный пример `after-04`, не установщик: он включает форму, обмен с сервером, SQLite и тесты.

Ты совмещаешь готовые части со своим проектом и отдельно меняешь `src/app.js`. Готовые форму и сервер не называй собственной реализацией: нужно разобраться в их работе и проверить её.

Пакет `H3/foundation` или `H4/foundation` передаёт преподаватель **после своего разрешения**. Публикация инструкций всех шести работ не разрешает выдачу или публикацию закрытых комплектов.

- Закрытые пути у преподавателя: `dist/handoffs/H3/foundation` и `dist/handoffs/H4/foundation`. Это не `public` и не автоматическая выдача по дате.
- `manifest.json` описывает состав и версию пакета.
- `examples/student-change.diff` показывает образец небольшой правки курсора.

**Diff** это сравнение старых и новых строк: `-` обозначает удаление, `+` добавление. Эти знаки относятся к сравнению, их не добавляют в код. Свою версию нужно сравнить с образцом, а не заменить им вслепую.

Различай две папки:

- **Собственная папка** нужна, чтобы продолжать поиск, запускать приложение и сохранять исходники.
- **Справочная папка** `_teacher-reference/foundation` содержит полученный образец только для чтения.

Перенос разрешённых частей выполняют по текущей инструкции выданного комплекта и после согласования с преподавателем. Наличие образца само по себе не разрешает замену проекта.

## Как заявка попадает с экрана в файл

Пример: человек пишет в Campus «Не работает проектор в 305».

- **Форма** объединяет сведения об одной заявке.
- **Поля** это отдельные места ввода: **«Краткий заголовок»** (`title`), **«Описание»** (`description`), **«Место»** (`location`), выбор категории (`category`) и приоритета (`priority`).
- **Клиент**, код страницы в браузере, показывает форму и принимает ввод. Кнопка **«Создать»** отправляет форму.
- **Сервер** здесь программа на Node.js: она получает обращения и сохраняет заявки.
- **Запрос** это сообщение браузера серверу.
- **Ответ** это сообщение сервера с результатом.
- **API** это согласованные способы общения программ: куда обратиться, какие поля передать и какой ответ ждать.

Сервер не обязательно удалённый компьютер: в этой работе браузер и программа сервера запущены на твоём компьютере. Без правил API сервер не узнает, хочет браузер прочитать список или добавить заявку.

Campus использует HTTP, правила передачи запросов и ответов. У запроса есть адрес и метод, то есть вид действия:

- `GET /api/tickets` читает список, не создавая записей.
- `POST /api/tickets` создаёт заявку. Адрес тот же, действие другое.

**Endpoint** это точка обращения к API, определяемая методом вместе с путём. По одному пути `/api/tickets` сервер выполняет разные действия для `GET` и `POST`. Открывая адрес в новой вкладке, ты делаешь `GET`; создание проверим кнопкой формы.

Тело POST содержит поля заявки. Они передаются в JSON, структурированном тексте с именами и значениями:

```json
{"title":"Не работает проектор в 305","category":"equipment","priority":"normal"}
```

- `title` это заголовок;
- `equipment` означает оборудование;
- `normal` означает обычный приоритет.

В готовом `src/api-client.js` функция `createTicket` отправляет такие поля серверу. Тот проверяет ввод, записывает допустимую заявку в файл SQLite и отвечает JSON с назначенным `id`.

SQLite работает с файлом прямо из программы; отдельный сервер базы данных не нужен. Карточки в браузере только показывают записи из ответа.

- **Процесс** это работающая программа. Если держать новую заявку только в его памяти, остановка программы потеряет её.
- **База данных (БД)** здесь файл, который остаётся на диске после остановки.

В полученной основе уже используется SQLite. В 04 проверим повторное открытие того же файла, а не будем писать хранение заново.

Различай результат HTTP и поля заявки:

- HTTP `201` в ответе значит **«создано»**.
- HTTP `400` значит **«неверные данные запроса»**. Коды ответа не являются командами.
- Поле `status: "new"` в JSON относится к состоянию заявки **«Новая»**, а не к HTTP-коду.
- `id` обозначает одну запись, не число карточек: **на новой базе после первого создания** будет 13 записей, а у новой заявки ID `113`. Поиск может скрыть часть карточек.

Твоя правка касается ввода следующей заявки. **Фокус** означает активное поле: туда попадает текст с клавиатуры, в текстовом поле виден курсор.

1. Отправка формы в коде называется `submit` и уже вызывает `createTicket`.
2. После успеха `form.reset()` очищает поля.
3. Сразу за ним твой `form.elements.title.focus()` вернёт курсор в **«Краткий заголовок»**.

**При ошибке поля и поиск должны остаться для исправления.**

Пошаговые действия, места щелчков и снимки находятся в [guide.json](guide.json). Ниже условия переноса и проверки.

## Проверь форму и API

Сначала выберем файл для учебных заявок. **Переменная окружения (environment variable)** `SERVICEDESK_DB` это именованная настройка терминала, которую сервер читает при запуске.

В PowerShell запись `$env:SERVICEDESK_DB = ...` задаёт её значение, путь к файлу. Она не запускает сервер и не создаёт заявку.

Если сервер работает, останови его **Ctrl+C в его терминале** и дождись строки ввода. **F5** обновляет только страницу и сервер не останавливает.

В терминале своей папки задай отдельную учебную БД. Если имя уже использовано, выбери новое без удаления старой базы:

```powershell
$env:SERVICEDESK_DB = 'stage03-04-check.db'
npm.cmd start
```

1. Первая команда выбирает файл базы. Имя без папки означает файл в папке запуска.
2. Вторая запускает программу сервера. Обычно вывод содержит `http://127.0.0.1:4173`.

Например, при запуске из `C:\Users\Анвар\Campus-ServiceDesk` путь будет `C:\Users\Анвар\Campus-ServiceDesk\stage03-04-check.db`. Возьми фактическую папку из строки PowerShell и **запиши свой полный путь для 04**.

- `127.0.0.1` означает свой компьютер; `localhost` тоже имя для обращения к своему компьютеру.
- `4173` это порт, по которому браузер обращается к программе.
- Путь `/api/tickets` после порта выбирает обращения за заявками. Открытие этого адреса в новой вкладке выполнит `GET`, не `POST`.

Используй фактический адрес из вывода: скопируй его в адресную строку браузера и нажми **Enter**. Пока сервер работает, этот терминал занят; для других команд открой отдельный.

Нет адреса: сначала прочитай ошибку терминала. `EADDRINUSE` означает занятый порт; проверь, не работает ли прежний сервер в твоих терминалах, и останови его. Не завершай неизвестные процессы. Если причина неясна, передай текст преподавателю. Если адрес есть, но страница сообщает «API недоступен», проверь, что открыл этот адрес, а не `index.html` как файл.

На чистом файле видны 12 исходных записей 101..112 при пустом поиске. Заполни форму вымышленными учебными данными без персональных сведений: заголовок из примера, описание «Учебная проверка», место «305», категория «Оборудование», приоритет «Обычный».

Чтобы увидеть обмен с сервером, перед отправкой открой в браузере **инструменты разработчика (DevTools)**:

1. Нажми **F12** или **Ctrl+Shift+I**.
2. Выбери **«Сеть» (Network)**; скрытая вкладка может находиться в меню **»**. Это журнал запросов браузера и ответов сервера.
3. Выбери **«Все» (All)** и введи `/api/tickets` в фильтр, чтобы видеть только обращения за заявками. Пустой журнал до отправки допустим.
4. После нажатия **«Создать»** открой строку запроса.

В журнале:

- **«Заголовки» (Headers)**: поля **Request Method** и **Status Code** показывают метод и код ответа.
- **«Полезная нагрузка» (Payload)** показывает отправленные поля.
- **«Ответ» (Response)** или **«Предпросмотр» (Preview)** показывает полученный JSON.

Ожидается `POST` с `201`, назначенным сервером ID и `status=new`. Только первая новая запись на чистой базе имеет ID `113`; **запиши фактический ID**. В следующем `GET` списка должна быть та же запись.

- Строк с одинаковым путём может быть несколько: различай их по **Request Method**.
- Если **Payload** нет, возможно, выбран `GET`.
- Если запросов не видно, убери фильтр, проверь запись журнала и адрес сайта.

**Не отправляй форму повторно только ради записи в Network**: сначала выясни, была ли заявка уже создана.

Прежде чем смотреть ответ в **Network**, проверь свою правку:

1. После успешного ответа, **не щёлкая мышью по полям**, набери несколько букв. Они должны появиться в поле **«Краткий заголовок»** (`title`).
2. Удали пробные буквы без отправки.
3. Сверь сохранённый поисковый запрос, затем при необходимости очисти поиск и найди карточку.

Текущий поиск сохраняется: новая карточка может не соответствовать запросу.

Проверка допустимости ввода называется **валидацией**. Браузер помогает быстро исправить форму, а сервер проверяет любой запрос, в том числе отправленный другой программой без формы. Оставь остальные поля заполненными и поисковый запрос прежним.

1. Оставь **«Краткий заголовок»** (`title`) пустым и нажми **«Создать»**. Обязательность поля (`required`) остановит отправку в браузере: появится предупреждение, нового `POST` не будет.
2. Затем нажми в поле пробел **ровно три раза** и отправь форму снова. Этот ввод проходит проверку обязательного поля, но сервер убирает крайние пробелы (`trim`) и отклоняет пустой результат с `400`.

На странице должно появиться сообщение, что заголовок не должен состоять только из пробелов. Остальные поля и поиск сохраняются, ложного успеха нет. Снимок `create-error` показывает случай трёх пробелов, не предупреждение браузера.

Отдельная проверка сервера обходит форму: помощник отправляет HTTP-запрос напрямую на фактический адрес твоего работающего сайта.

- Запрос: `POST /api/tickets` с пустым `title` и допустимыми `category: "equipment"`, `priority: "normal"`.
- Ответ: код `400` и `validation_error`, название ошибки проверки.
- Список из `GET /api/tickets` до и после должен совпасть.

Код, настройки и базу напрямую не менять, проверки формы не отключать. В **Plan** вставь запрос ниже и нажми **Enter**. Если режим или разрешения не позволяют выполнить HTTP-запрос, остановись для ручной проверки преподавателем без изменения прав:

```text
Прочитай в TASK 03 проверку отказа сервера. Выполни её на моём работающем сайте: отправь заявку с пустым полем «Краткий заголовок».

Покажи ответ сервера и сравнение списка до и после. Код, настройки и базу напрямую не меняй, проверки формы не отключай. При запрете доступа остановись. Коммиты и отправку не выполняй.
```

Если видно «Создана заявка #…», но затем «Список не обновился», POST уже сохранил запись, а следующий GET не удался. Не отправляй форму повторно. Восстанови доступ к серверу, обнови страницу и проверь записанный ID через GET.

Дополнительные способы чтения одной заявки и смены её состояния уже есть в полном примере и готовых тестах; писать их самостоятельно не требуется. В foundation уже SQLite: потеря записи при перезапуске не считается нормой этапа 03.

## Сохранение

После проверок формы и API в 03:

1. Прочитай `git status --short --untracked-files=all`, `git diff`, новые файлы открой отдельно.
2. В **«Управлении версиями»** кнопкой **+** выбери только проверенные исходники и инструкции. Исключи `_teacher-reference/`, БД (`.db`, `.db-wal`, `.db-shm`), `.env` и ключи.
3. Выполни `git diff --cached`, прочитай вывод, затем:

```powershell
git commit -m "Подключение готовой основы"
git rev-parse HEAD
```

Если новых изменений нет, покажи существующий SHA. Отправка в свой форк по договорённости допустима после сверки push-адреса. MR, CI, Issue, слияние в main и REPORT не обязательны. Локальную версию не называй отправленной.

Теперь переходи в 04 с теми же папкой, веткой и базой. Коммит сохраняет исходники; сохранение заявки после остановки пока не проверено.

## Успешный результат

- Свой поиск 02 сохранён; известны SHA исходной версии и версия foundation.
- Готовая форма создаёт через `createTicket`; `POST` возвращает `201`, серверный ID и `new`, `GET` возвращает запись. После успеха фокус возвращается в `title`.
- Пустой `title` не создаёт заявку; видны понятная ошибка и отсутствие ложного успеха, серверная проверка подтверждена отдельно.
