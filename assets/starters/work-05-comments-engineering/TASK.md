# 05. Необязательные комментарии и review

**Цель:** По желанию проверить комментарии или одно замечание к коду, сохранив общий результат поиска, формы/API и SQLite.

**Рабочая ветка:** `feature/ticket-comments`

## Место в маршруте

**05 целиком необязателен**. Можно выбрать комментарии, review или правила агента, а можно пропустить всё без штрафа и получить ту же высокую оценку по общему минимуму. Дополнение не становится условием допуска к 06.

`after-05` обозначает полную учебную версию с комментариями, а не обязательный результат каждого студента.

Продолжай прежнюю папку с принятой основой 03/04. Если комментарии уже предоставлены готовыми, называй их **готовым дополнением**. Если их нет, объём реализации согласуй отдельно; не выдавай полную реализацию за короткую обязательную правку.

- **Для review** можно остаться на принятой версии без нового коммита.
- **Для правок** сначала просмотри `git status --short`, сохрани нужное и только из чистой принятой версии создай `feature/ticket-comments`.

Существующую ветку не пересоздавай, на `main` автоматически не переключайся. Сохрани заметки и настройки; `recovery` распаковывается только в новую папку.

## Задание

**Комментарий**, отдельная запись к конкретной заявке. `ID` означает её номер: «Проверен HDMI» у №101 не относится к №102 и не заменяет описание №101.

**Review** означает второе чтение кода для поиска возможной ошибки, без автоматического исправления. Выбор комментариев не обязывает выполнять review, и наоборот.

OpenCode помогает читать и менять файлы. В режиме **Plan** сначала просим объяснение без правок; в **Build** разрешаем только согласованные изменения.

В Git различай:

- **Ветку**, отдельное направление работы.
- **Коммит**, сохранение выбранных файлов.
- **SHA**, обозначение конкретного сохранения.

`git status --short` показывает незаписанные изменения; пустой ответ означает, что их нет.

1. С преподавателем выбери комментарии, review, правила агента или пропуск. Пропуск не требует отчёта задним числом.
2. Для комментариев в OpenCode Plan выясни, что уже входит в основу. Если нужна правка, согласуй пути, затем разреши её в Build. Не меняй поиск, создание и хранение ради дополнения.
3. Проверь выбранные комментарии в браузере и API по разделу ниже. Готовый код не засчитывай как написанный самостоятельно.
4. Для выбранного review открой новый разговор и запроси чтение без правок. Одно замечание сверь с файлом и воспроизведением. Если ошибок нет, придумывать их не нужно.
5. Сохрани только реально сделанные изменения, покажи результат и своё решение. MR, Issue, CI, AGENTS, skill и REPORT не являются обязательными условиями общего курса.

**Plan** для комментариев:

```text
Посмотри, что уже готово для комментариев в моей папке. Ничего не меняй.

Где вводится комментарий и как он сохраняется? Покажи файлы и объясни, как проверить готовую часть по разделу «Проверка выбранных комментариев» в TASK.md занятия 05.

Если чего-то не хватает, скажи об этом и подожди моего решения.
```

## Проверка выбранных комментариев

**API** здесь набор адресов и правил обмена страницы с сервером. `GET` читает данные, `POST` отправляет данные для добавления. SQLite хранит записи в файле базы.

Найди форму, адреса комментариев и сохранение; попроси агента указать соответствующие файлы. Проверяется **собственная рабочая папка**, а не запуск справочной копии. Сохрани поиск, создание заявок и прежнюю базу.

- **Автоматический тест** сам выполняет заранее написанный сценарий и сравнивает результат с ожидаемым. Команда `npm.cmd test` запускает такие тесты.
- **Ручную проверку** ниже выполняешь ты в браузере: она показывает поведение твоей запущенной версии, включая ввод и обновление страницы.

Один способ не заменяет другой.

Запусти `npm.cmd start` с прежним `SERVICEDESK_DB`. На №101 добавь «Проверен HDMI» и второй синтетический текст. Нажми `F5`.

В готовом приложении комментарии загружаются **при изменении ID**, а не при открытии страницы; начальное значение поля уже `101`. Чтобы загрузить список:

1. Введи `102` и щёлкни вне поля.
2. Введи `101` и снова щёлкни вне поля.

Повторный ввод того же `101` может не вызвать загрузку. Оба текста должны появиться в порядке добавления.

Останови `Ctrl+C` и снова запусти сервер в том же терминале **с тем же файлом базы**. Открой страницу и повтори смену ID: `102` → щелчок вне поля → `101` → щелчок вне поля. Либо прочитай записи напрямую через `GET /api/tickets/101/comments` на адресе своего сервера.

Пустая область сразу после обновления или нового открытия страницы **не доказывает потерю комментариев** в базе. Если записи не вернулись и через `GET`, сначала сверь папку запуска и `SERVICEDESK_DB`. Не удаляй комментарии или файл базы ради проверки.

Для прямой проверки допиши к адресу своего сервера `/api/tickets/101/comments` и открой его в отдельной вкладке. Это `GET`: ожидаются оба текста.

**JSON**, формат ответа с именованными полями, позволяет увидеть автора и текст каждой записи. **HTTP-статус**, число в ответе сервера, сообщает итог запроса.

Пустое поле браузер может отклонить до отправки. Для проверки именно сервера попроси агента выполнить следующие запросы на твоём работающем адресе без правок кода и показать ответы:

| Запрос | Ожидаемый результат |
| --- | --- |
| `GET /api/tickets/101/comments` | 200, список до проверки |
| `POST /api/tickets/101/comments`, JSON `{"author":"Студент","text":""}` | 400, неверный ввод, комментарий не создан |
| `GET /api/tickets/999999/comments`, предварительно убедившись, что такого ID нет | 404, `ticket_not_found` («заявка не найдена») |
| Повторный `GET /api/tickets/101/comments` | 200, число записей не выросло |

В полном примере успешное добавление даёт `201` («создано») и событие `comment_added` («добавлен комментарий») в `/api/tickets/101/history`. **История необязательна**; проверяй её только при выборе этого дополнения.

## Review и правила по желанию

**Review** означает проверку кода чтением и воспроизведением возможных ошибок. Оно **не разрешает автоматическое редактирование**.

Перед чтением укажи файлы или коммит. **Diff** показывает старые и новые строки. Например:

```diff
- const limit = 10;
+ const limit = 20;
```

Прежнее значение `10` удалено, новое `20` добавлено. Знаки `-` и `+` принадлежат сравнению, **их не вводят в код**.

В VS Code открой **Управление версиями** и выбери изменённый файл. Новые файлы прочитай отдельно.

В отдельном разговоре OpenCode выбери **Plan** и отправь:

```text
Прочитай мои изменения и связанные тесты без правок. Могут ли созданные заявки потеряться после остановки и нового запуска с тем же файлом базы? Если в моей работе есть комментарии, посмотри и их.

Если заметишь проблему, покажи место в файле и объясни, как мне её проверить. Отдели предположение от того, что проверил сам.

Если подтверждённых ошибок нет, так и скажи.
```

Разбор выполняется **без правок, commit и push**. Для замечания нужны:

- Путь и строки файла.
- Входные данные.
- Ожидаемый результат.
- Способ воспроизведения.

Предположение по коду не выдаётся за выполненную проверку. **Если подтверждённых ошибок нет, это допустимый итог**.

Сначала объясни, что может сломаться и как это затронет пользователя. Затем найди указанный файл и повтори сценарий сам.

Например, пустая область комментариев после `F5` ещё не подтверждает потерю данных: явно загрузи список сменой ID `102 → 101` или через `GET` с прежней БД.

Доказательство связывает **ввод, ожидание и факт**: «До перезапуска у №101 было два текста; после запуска с той же БД GET вернул оба». В этом сценарии потеря данных не подтвердилась.

Если `GET` пуст, сначала сверь папку запуска и путь БД. Ошибка подтверждается расхождением в повторённом сценарии, а не уверенным тоном ответа агента. Неудавшаяся проверка остаётся непроверенной.

Подтверждённое исправление разрешай только в согласованных путях; повтори затронутый сценарий и `npm.cmd test`. Объясни отклонение неподтверждённого замечания. Таблица и полный чат не нужны.

`AGENTS.md`, необязательный текстовый файл с правилами для агента в проекте. Он помогает не повторять одни и те же поручения. Если практику не выбираешь, создавать его не нужно.

Если выбираешь, сохрани существующие правила и добавь конкретные действия:

- Читать `TASK` и согласовать пути.
- Сохранять **контракты**, согласованные поля и результаты.
- Выполнить тесты, показать diff и непроверенное.

**Сам текст не блокирует команды технически**.

Открой этот файл в корне проекта в VS Code. Инструкция «не читать внешние папки» сообщает агенту правило; запрет доступа в настройках OpenCode технически отклоняет попытку чтения.

Запись в `AGENTS.md` не создаёт такой запрет и не отменяет существующий. Результат инструкции виден в фактических действиях и проверках, а не только в обещании агента.

**Skill**, повторяемая инструкция для отдельной задачи. По желанию сохрани список в `.agents/skills/acceptance-check/SKILL.md`:

```markdown
---
name: acceptance-check
description: Проверить выбранное изменение Campus ServiceDesk.
---
1. Прочитай критерии TASK и git diff, новые файлы открой отдельно.
2. Не меняй программу; выполни npm.cmd test и покажи фактический итог.
3. Сопоставь критерии с тестами и выполненным ручным сценарием.
4. Назови непроверенное. Не придумывай результаты.
```

Попроси выполнить список без правок. Если клиент не обнаружил skill, выполни пункты явно и назови фактический способ.

Например, вывод тестов подтверждает их запуск, а просмотренный diff показывает проверенные изменения. Одно сообщение «skill выполнен» этого не доказывает.

## Сохранение

1. Прочитай `git status --short`, `git diff`, новые файлы отдельно.
2. В **Управлении версиями** выбери проверенное кнопкой **+**. Файл базы, `.db-wal`, `.db-shm`, `.env` и ключи не выбирай.
3. Прочитай `git diff --cached`: он покажет выбранное для коммита. Создай локальный коммит **только если были правки**.

Решение review можно объяснить устно или свободной заметкой. Продолжай ту же папку в 06 после разрешения финального комплекта.

**До разрешения не переноси готовую AI-подсказку** в приложение; порядок выпуска не меняется.

## Успешный результат

- Выбранное дополнение проверено и объяснено; либо 05 явно пропущен без штрафа.
- Для комментариев: сохранность после обновления/рестарта, порядок текстов и отказ пустого ввода подтверждены.
- Для review: замечание проверено по файлу и сценарию, решение принято человеком.
- Готовые части названы честно; поиск, форма/API и SQLite сохранены.

## Не засчитывается, если

- Выбранное дополнение объявлено проверенным без запуска или объяснения.
- Готовый код назван самостоятельной реализацией.
- Замечание агента названо фактом без проверки.
- Пропуск дополнения ошибочно объявлен провалом общего обязательного минимума.

## Что сдавать

- Только для выбранного дополнения: показ результата и короткое объяснение проверки.
- При правке: просмотренный diff и SHA, без обязательного отчёта, MR или CI.
- При пропуске: дополнительных материалов сдавать не нужно.
